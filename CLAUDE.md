# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

"SISREP": sistema web de inventario, compras y ventas de repuestos para camiones de alto tonelaje (cliente: **JISSACRUZ**, Santa Cruz, Bolivia). Implementación en curso siguiendo [PLAN.md](PLAN.md) fase por fase / sprint por sprint (ver "Estado general" al inicio de ese archivo — avance ~90%: Sprints 1–3 funcionales de punta a punta en la UI y el grueso del Sprint 4 construido —dashboard con KPIs, los 4 reportes con exportación PDF/Excel y la pantalla de Configuración—; quedan el **despliegue en Vercel** y la UAT; el manual de usuario ya está en `docs/`. Los Sprints 5 y 6 son alcance adicional pedido por el cliente y están cerrados en código y BD). Todo el dominio, la base de datos y la UI están en español; mantener el español en nombres de tablas, rutas, componentes y textos de interfaz.

## Comandos

```bash
npm run dev      # servidor de desarrollo (localhost:3000) — NO usar --turbo (rompe con @supabase/supabase-js)
npm run build    # build de producción
npm run start    # sirve el build de producción
npm run lint     # eslint (next/core-web-vitals + next/typescript)
```

No hay suite de tests configurada. La verificación de backend se hace corriendo los scripts SQL en `supabase/` (ver siguiente sección) directamente en el SQL Editor de Supabase, no con un runner local.

Después de tocar código, para verificar suele bastar `npm run build` / `npm run lint`; no hace falta levantar el server local (la "lentitud al entrar a páginas" en dev es solo la compilación on-demand de Next, no un problema real).

## Base de datos (Supabase)

Scripts en [supabase/](supabase/README.md), pensados para pegarse en el SQL Editor de Supabase — no hay migraciones vía CLI/ORM.

- **Dos bases Supabase separadas: desarrollo (`dynamiccoding01`) y producción (`jissacruzscz-spec`).** Cada cambio de esquema es **un script nuevo numerado** (van hasta el `43`) que hay que correr en el SQL Editor de **ambas** bases y, además, reflejar en `supabase/produccion_setup.sql` (el instalador consolidado para bases nuevas). Al terminar una tarea con SQL, dejar anotado en el PLAN_N de la tanda "⚠️ falta correr `NN_*.sql` en dev + prod" hasta confirmarlo. `produccion_setup.sql` incluye todos los scripts hasta el `43` (los 35–38 se sumaron el 27 sep 2026; antes faltaban).
- Proyecto nuevo: correr `00_setup_completo.sql` completo (concatena 01→05 como una transacción implícita) y luego `produccion_setup.sql` para los incrementos posteriores.
- Cambios incrementales sobre una base existente: correr solo el script nuevo correspondiente a la fase (p. ej. `09_busqueda_productos.sql`), nunca repetir `00`.
- `06_verificacion.sql` y `08_verificacion_rls_vendedor.sql` son pruebas end-to-end con rollback intencional; requieren primero crear un usuario de prueba `admin` y `vendedor` respectivamente desde Supabase Auth (`user_metadata: { "rol": "admin" | "vendedor" | "cajero" }` — el trigger `on_auth_user_created` crea la fila en `perfiles`).
- `07_fix_fifo_desempate.sql` es un parche histórico; no se corre en instalaciones nuevas.

## Arquitectura

**Server Components por defecto; Server Actions (`"use server"`, en `actions.ts` por módulo) para toda mutación; Route Handlers solo bajo `/api/pdf/*`** para generar PDFs con `@react-pdf/renderer` (no hay API REST pública). Cada módulo de `app/(dashboard)/<modulo>/` sigue el mismo patrón: `page.tsx` (Server Component, carga inicial de datos) + `<modulo>-explorer.tsx` (Client Component, tabla/filtros con `@tanstack/react-table`) + `<modulo>-form.tsx` (react-hook-form + zod) + `actions.ts` (Server Actions, valida con el schema de `lib/validations/<modulo>.ts` antes de tocar Supabase). Módulos existentes: `productos`, `inventario`, `kardex`, `proveedores`, `compras`, `clientes`, `proformas` (con detalle/edición en `proformas/[id]` y alta en `proformas/nueva` — pasó de modal a página), `cotizacion` (**solo productos S/F**; desde PLAN_4 **persiste con historial** como una proforma — tablas `cotizaciones`/`cotizacion_items`, `COT-0001`, historial en `page.tsx` + alta en `cotizacion/nueva`, PDF en `/api/pdf/cotizacion/[id]`), `ventas` (el POS en `ventas/pos.tsx`; desde PLAN_5/T5 **ya no cobra**: crea un pedido pendiente que la Caja confirma), `caja` (**PLAN_5/T5**: lista los pedidos pendientes y el cajero los cobra/confirma o cancela), `traspasos` (el módulo "Pedido"), `sucursales`, `unidades-medida`, `reportes`, `dashboard`, `configuracion`.

**PDF y Excel**: cada documento PDF vive en `lib/pdf/<x>-document.tsx` y se sirve por su Route Handler en `app/api/pdf/<x>/` (`kardex`, `proforma/[id]`, `venta/[id]`, `reporte`). La exportación a Excel es cliente puro vía SheetJS en [lib/excel/export-to-excel.ts](lib/excel/export-to-excel.ts). `dashboard` y `reportes` grafican con `recharts` (cargado en un componente `*-inner`/`*-chart` cliente); la lógica de los 4 reportes está en [lib/reportes.ts](lib/reportes.ts) + [lib/reportes-tipos.ts](lib/reportes-tipos.ts). El bloque **Rentabilidad** del dashboard (PLAN_6 · T3/T4: ingresos sin impuesto, costo de ventas FIFO, utilidad y margen bruto) muestra **con factura y sin factura en dos paneles que nunca se suman**; sale de la RPC `fn_rentabilidad_por_factura('hoy'|'mes'|'anio')` (script `43`, solo admin, 2 filas fijas), y el reporte **Rentabilidad** de `fn_reporte_rentabilidad(desde, hasta, agrupacion)`. Ambas suman en SQL y cortan los períodos en hora de Bolivia (la `fn_resumen_rentabilidad` del script 42 quedó sin uso). Para cortar días en hora de Bolivia desde el servidor (Vercel corre en UTC) usar [lib/fechas-bolivia.ts](lib/fechas-bolivia.ts).

**El kardex es la fuente de verdad del stock, pero `productos.stock_actual` es una columna cacheada** mantenida por el trigger `trg_kardex_stock` sobre cada insert en `kardex_movimientos` (no una vista) — un segundo trigger bloquea que un `UPDATE` directo sobre `productos` la modifique. Valorización FIFO por lotes vía `cantidad_restante_lote`, con desempate por la columna `consecutivo` (identity) cuando dos lotes comparten `creado_en`.

**Toda operación que mueva stock pasa por una función Postgres `security definer` vía `supabase.rpc()`** — nunca updates directos ni múltiples queries no atómicas desde el cliente: `fn_registrar_venta`, `fn_recibir_orden_compra`, `fn_convertir_proforma_a_venta`, `fn_ajuste_stock`. `ventas` y `kardex_movimientos` no tienen política RLS de `insert`: solo estas RPC (que corren como `security definer`) pueden escribir ahí. Ver ejemplo de uso en [app/(dashboard)/compras/actions.ts](<app/(dashboard)/compras/actions.ts>): `supabase.rpc("fn_recibir_orden_compra", { p_orden_id })` seguido de `revalidatePath` en cada ruta afectada (compras, inventario, kardex, productos).

Búsqueda avanzada de productos (código, equivalente, descripción, línea/marca, vehículo compatible) va por una sola RPC, `fn_buscar_productos(texto, campos text[])`, reutilizada por catálogo, compras, ventas/POS y proformas — no reimplementar el filtro en el cliente. El usuario elige por qué campos buscar (multi-selección) con el componente compartido [components/shared/criterios-busqueda.tsx](components/shared/criterios-busqueda.tsx); esos criterios (`campos`) se pasan a la RPC, que filtra solo por los marcados (OR entre ellos; arreglo vacío ⇒ busca en todos). Los `id` de los criterios en ese componente deben coincidir con los que evalúa el SQL. **La versión vigente de la función es la del `supabase/25_busqueda_original_medida.sql`**: suma los criterios `original` (códigos OEM) y `medida`, e incluye el `unaccent` del script 26 (buscar `valvula` encuentra `VÁLVULA`). Usa `EXISTS` para las tablas hijas, sin `LEFT JOIN` ni `DISTINCT`. ⚠️ Antes de reescribirla, confirmar qué está corriendo con `select prosrc from pg_proc where proname='fn_buscar_productos'` — el repo ya tuvo dos definiciones en conflicto.

**Auth y roles**: [lib/auth/session.ts](lib/auth/session.ts) expone `getPerfil()` (cacheado por request con `cache()` de React) , `rutaInicio(rol)` (pantalla de inicio de cada rol: admin → `/dashboard`, cajero → `/caja`, vendedor → `/proformas`; la usan el login, la raíz `/` y las guardas) y `requireRol([...])` / `requireAdmin()` para guardas de página (si el rol no corresponde, redirige a su `rutaInicio`). `app/(dashboard)/layout.tsx` ya valida sesión/`activo` y hace `signOut()` + redirect a `/login` si falla; las páginas exclusivas de admin deben llamar `requireAdmin()` igual, porque el layout no filtra por rol. **Tres roles** (`type Rol = "admin" | "vendedor" | "cajero"` en [components/shared/nav-items.ts](components/shared/nav-items.ts), `check` en `perfiles.rol` desde el script `38`): `admin` (todo); `vendedor` (Productos/Inventario en lectura, Pedidos, Clientes, Cotización, Proformas y **crea pedidos en el POS**); `cajero` (Productos/Inventario en lectura, Clientes, Cotización y **CAJA** — cobra/confirma los pedidos pendientes). **Ventas en dos pasos (PLAN_5/T5):** el POS (`ventas`, vendedor + admin) ya no cobra — arma un pedido pendiente `ventas_pendientes` (`PDV-0001`, sin tocar stock) vía `fn_crear_venta_pendiente`; en **CAJA** (`caja`, cajero + admin) el cajero elige tipo de pago + con/sin factura y **confirma** con `fn_confirmar_venta_pendiente`, que corre `fn_registrar_venta` (atómica: revalida stock, FIFO, kardex, `VEN-xxxx`, factura) o **cancela** con `fn_cancelar_venta_pendiente`. `fn_registrar_venta` sigue siendo atómica; la venta resultante queda con `vendido_por` = el cajero que confirma (el vendedor original queda en `ventas_pendientes.creado_por`). `nav-items.ts` es la matriz por ítem de navegación; FLUJO.md §10 la matriz completa. Las páginas por rol usan `requireRol` (p. ej. Proformas y Pedidos: admin + vendedor; Caja: admin + cajero; POS: admin + vendedor) y sus acciones de escritura vuelven a chequear el rol, porque una Server Action se puede llamar directo. RLS activo en todas las tablas; sin registro público, usuarios creados por invitación del admin desde Supabase Auth (o desde **Configuración → Usuarios**). Desde el script `30`, el **vendedor solo ve las ventas, proformas y pedidos de su sucursal** (política de `select` con `fn_es_admin() or ... = fn_mi_sucursal()`); catálogo, stock por sucursal y kardex los ven todos. **Ojo:** un perfil con `sucursal_id` en null deja de ver esos listados, sin error.

**Tres clientes Supabase distintos según contexto** — no mezclarlos: [lib/supabase/server.ts](lib/supabase/server.ts) (`createClient()`, anon key + cookies, Server Components/Actions), [lib/supabase/client.ts](lib/supabase/client.ts) (browser, Client Components) y [lib/supabase/admin.ts](lib/supabase/admin.ts) (`createAdminClient()`, service_role, marcado `import "server-only"` — solo para operaciones que deben saltar RLS deliberadamente, nunca importar desde código que corra en el navegador). `middleware.ts` refresca el token de sesión en cada request via su propio `createServerClient`.

**Guardado de producto:** crear y editar producto pasan por la RPC transaccional `fn_guardar_producto` (script `29`, extendida por 22–24) — cabecera y todos los hijos (equivalentes, **originales OEM**, **medidas**, vehículos, precios por mayor) en una sola transacción. No volver al patrón de `delete` + `insert` sueltos desde la Server Action.

**Tres niveles de código de producto:** `productos.codigo` (el de la tienda) · `producto_codigos_originales` (OEM del fabricante, N por producto) · `producto_codigos_equivalentes` (de otro fabricante, N por producto). Ninguna de las dos tablas guarda `fabricante`. **Unidades de medida sin conversión:** un producto se vende solo en su unidad; el kardex y el FIFO no la miran.

**Numeración correlativa** `PRO-0001` / `VEN-0001` viene de secuencias Postgres + trigger `BEFORE INSERT` (script `02_secuencias_triggers.sql`) — nunca calcular el siguiente número en la aplicación.

**Precio de venta y costo:** `productos.precio` es el precio de **venta** y **no hay columna de costo** — el costo vive en los lotes del kardex y se deriva con [lib/costos-server.ts](lib/costos-server.ts). Regla de negocio (script `32`): **el precio de venta debe ser mayor al costo de compra**, exigida en el formulario, en la Server Action y por un `check` en `orden_compra_items`. El precio de venta se fija **al armar la orden de compra** (columna `precio_venta`) y `fn_recibir_orden_compra` lo aplica a `productos.precio` **al recibir**, no al crear la orden.

**Descuentos y precio mínimo (PLAN_6, script `41`)**: **Proforma y POS ya no admiten descuentos** (ni global ni por línea) y el **precio unitario no puede bajar del precio del sistema para esa cantidad** — el precio por mayor vigente de la escala alcanzada, o el precio normal (`fn_precio_minimo(producto, cantidad)` en la BD, `precioSegunCantidad` + `validarPrecioMinimo()` de [lib/precios-mayor-server.ts](lib/precios-mayor-server.ts) en la app). Lo exigen el trigger de `proforma_items`, un trigger en la cabecera de `proformas` y `fn_crear_venta_pendiente`, solo sobre filas nuevas (las proformas históricas con descuento siguen legibles y convertibles). Cotización S/F sí conserva descuento y precio editable. Históricamente se guarda tipo (`porcentaje` | `monto_fijo`) + valor aplicado, no solo el resultado. `impuesto_porcentaje` es un campo manual (default 0), sin IVA automático. En proformas, el trigger `fn_proforma_items_validar` recalcula `subtotal_linea` y valida límites de descuento en cada insert/update — las proformas no pasan por RPC porque no tocan stock, así que ese trigger es su única red de integridad (a diferencia de ventas, donde `fn_registrar_venta` hace ese trabajo).

**Con/sin factura y tipo de pago** (scripts `36`–`37`): `productos.con_factura boolean` marca el producto como "S/F" (badge en explorer/POS/cotización); la **venta** guarda su propio `ventas.con_factura` (elegido al cobrar, default derivado del carrito) y ese flag alimenta la separación Con factura / Sin factura en Reportes. `ventas.tipo_pago` (Efectivo/QR/Transferencia/Tarjeta/Crédito, lista fija en [lib/tipos-pago.ts](lib/tipos-pago.ts)) lo guarda `fn_registrar_venta` y sale en el PDF de la factura. La cotización (`cotizacion`) filtra a solo productos `con_factura = false`. **Desde PLAN_6 · T4 (script `43`):** un producto S/F **nunca** se vende con factura (`fn_registrar_venta` lo rechaza y, si no le pasan `con_factura`, lo deriva de los productos), y un **pedido del POS o una proforma no mezclan** productos con factura y S/F (validado en la action con [lib/factura-server.ts](lib/factura-server.ts) y en la BD). El criterio para separar ganancias es `ventas.con_factura` (si se emitió factura), no el tipo de producto.

Moneda: Boliviano (Bs). **Multi-sucursal** (Sprint 5, scripts `12`–`20`): tabla `sucursales`, stock cacheado por sucursal en `producto_stock_sucursal`, `kardex_movimientos.sucursal_id`, perfil con sucursal asignada (`fn_mi_sucursal()`) y pedidos de traspaso entre sucursales (`PED-000001`, RPCs `fn_crear_pedido_traspaso` / `fn_enviar_traspaso` / `fn_recibir_traspaso` / `fn_cancelar_traspaso`).

## Reglas de ejecución (obligatorias)

- Antes de tocar un módulo, revisar su estado real en la columna **Estado** de PLAN.md (no asumir por el nombre de la carpeta ni por que exista un archivo que la funcionalidad esté completa o pulida — a ~90% lo que falta es transversal: despliegue en Vercel, UAT y manual, no la implementación de módulos).
- No introducir tecnologías fuera de las definidas en TRD.md sin consultarlo explícitamente.
- Toda operación que modifique stock debe pasar por las funciones RPC transaccionales — nunca actualizar stock desde el cliente ni con múltiples queries no atómicas.
- Ante ambigüedad no cubierta por los documentos, señalar la duda en lugar de asumir.
